## P1：可以開始，完整設備整合有前置條件

目前 `control.py` 的 Controller 每秒處理設備與持久化請求，Agent worker 在另一個執行緒工作。P1 的時間規則、presence、環境時鐘及 REST 設定可沿 Controller／SQLite 執行，不必經 Copilot Runtime 或 AG-UI 建立需求。因此 CHAT-01／02 不是這些模組開始開發的必要前置。

| P1 範圍 | 能否先執行 | 條件 |
| --- | --- | --- |
| 時間窗／presence 純判斷、環境時鐘、持久化與領域測試 | 可以 | 先以注入時鐘及假傳輸驗證；遵守已確認設定，規則預設關閉。 |
| 規則／環境 REST API 與設定頁 | 可以 | 沿用持久化請求與版本檢查，不以聊天完成作為設定生效條件；顯示 Controller 與請求狀態。 |
| 背景規則派送、明確啟用、手動覆寫與停用 | 有條件 | 先完成燈泡新舊指令仲裁、原始使用者意圖順序、pending 自動目標撤銷與過期目標阻擋，再允許規則控制共用設備。 |
| Light Agent 說明／停用規則草稿 | 可延後交付 | 首版使用 REST 設定入口即可；保留此為原計畫未完成項目。接入聊天後仍受 CHAT-01／02 限制。 |
| 聊天斷線／重啟後的完整端到端 P1 體驗 | 暫不宣告通過 | 等 CHAT-01／02 恢復實作並通過對應驗收。 |

`BulbController.process_requests()` 目前在 active action 存在時直接等待，沒有新目標取代與手動／自動來源仲裁。若直接疊加規則，舊自動目標可能延遲執行，且無法滿足手動操作優先的既定契約。這是 P1 完整設備整合的實際前置，不能以聊天修正延後作為略過理由。

Controller 程序本身停止時，背景規則也會停止；同程序內 worker 與控制迴圈的分離不等於整個服務永不中斷。P1 的規則、覆寫與環境狀態恢復仍須獨立設計及測試。

資料庫目前為 v4。原計畫的「P0 升 v5、P1 升 v6」尚未落實；P1 開發前須依實際遷移順序重新安排版本，不可假設 CHAT-01 的資料表已存在，也不可只改版本號而省略遷移測試。

時間與設備流程可獨立報告成功率、延遲與恢復時間；完整「聊天到設備」可靠性結論須等聊天缺口解決。P2 架構不需等待全部 P1 完成，但涉及新功能的量測必須等待該功能有可驗證的實作。

## 建議接續順序

1. 將 CHAT-01／02 保留為延後待辦，P0 整體維持尚未通過。
2. 開始 P1 純規則、環境時鐘、presence 資料契約與測試，同時建立 P2 情境／報告框架。
3. 完成燈泡仲裁、取代與撤銷舊自動目標的控制能力，再整合 P1 背景派送與設定頁。
4. 依序驗收時間規則、有人／無人、覆寫／恢復及 MQTT／Matter，產生分項 P2 報告。
5. 日後恢復 CHAT-01／02，補做完整聊天斷線／重啟驗收，再評估 P0 與跨階段整體通過。
