## Azure OpenAI 設定預留

`.env` 與 `.env.example` 預留以下欄位，目前可以留白；既有 MQTT 監測不依賴它們：

```dotenv
AZURE_OPENAI_ENDPOINT=
AZURE_OPENAI_API_KEY=
AZURE_OPENAI_DEPLOYMENT=
```

- `AZURE_OPENAI_ENDPOINT`：Azure 資源的 HTTPS Endpoint，例如 `https://YOUR-RESOURCE.openai.azure.com`。
- `AZURE_OPENAI_API_KEY`：該資源的 API Key。
- `AZURE_OPENAI_DEPLOYMENT`：實際建立的部署名稱；不假設與底層模型名稱相同。

先預留 API Key 模式的設定。Azure client、驗證及呼叫流程會在整合方案確認後實作；目前尚未執行模型呼叫。

## vLLM 備援設定預留

```dotenv
VLLM_BASE_URL=
VLLM_API_KEY=
VLLM_MODEL=
```

- `VLLM_BASE_URL`：OpenAI 相容 API base URL，包含 `/v1`，例如 `http://127.0.0.1:8000/v1`。
- `VLLM_MODEL`：伺服器提供的 served model name。
- `VLLM_API_KEY`：依伺服器驗證設定填入，未啟用驗證時可留白。

這些欄位也已預留於 `.env` 與 `.env.example`。實際模型與服務能力要在使用者填入後驗證，不假設現有服務已啟用自動工具呼叫。

欄位格式參考 [vLLM OpenAI 相容伺服器](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/)及 [serve CLI](https://docs.vllm.ai/en/stable/cli/serve/)。

## 首版整合邊界

- 保留原有冷氣監測，新增一台可控洗衣機、任務核准介面、執行服務及 Main Agent。
- Main Agent 自行選擇工具，反覆讀取設備／任務狀態、查電價、計算候選時段、驗證與提交計畫，以及查核執行結果、重新規劃。
- 工具的輸入與輸出使用明確資料型別；設備名稱、時段、費用與核准限制都由程式驗證。
- Agent 不持有核准權；使用者核准的限制及計畫版本保存於 SQLite，會改變任務的工具必須經過這些限制檢查。
- 本機執行器依核准計畫準時觸發操作，持續監測並產生事件；Agent 在事件發生後啟動多輪工具流程。既有任務執行不依賴模型隨時在線。
- Agent 的上下文、工具輸入／結果、決策摘要與使用的模型服務需要留存，供使用者查看；不將 MQTT 發送成功直接記為設備操作成功。
- 未來 Sub Agent 使用同樣的任務上下文及工具邊界回傳工作結果，由 Main Agent 協調；核准與執行限制仍共用，不建立第二套設備狀態。
- Matter、冷氣自動控制與實際電價接入為後續階段；Multi-agent 分工是明確的後續目標，不以首版單一 Main Agent 作為最終架構。

## 已接受的執行保護預設

以下技術預設已經使用者確認，實作時納入並保留設定調整方式：

- 每次 Agent 工作最多 15 次模型請求（包含備援嘗試），總時間最多 120 個真實秒；單次請求上限 20 個真實秒。
- Azure 不可用時切到 vLLM，保留已取得的工具結果，不因換模型重做已完成的設備操作。
- 模型逾時、工具輸入不合法或流程超限時，留下明確狀態及原因；既有核准任務由本機執行器持續處理。
- MQTT 操作使用命令識別碼與設備狀態確認；命令不保留為 retained 訊息。重複命令不得重啟行程。
- 操作確認預設等待 5 個真實秒；未取得確認時先查狀態並標示未知，不盲目重送啟動或當成完成。
- 相同異常在尚未處理完畢時合併，不因每兩秒收到遙測而重複啟動 Agent。

## 首版驗收情境

1. 使用者以自然語言提出含跨夜期限／安靜時段的需求，Main Agent 透過多輪工具取得資料、產生可驗證計畫，於核准後才執行。
2. 洗衣機依洗滌、漂洗、脫水前進，畫面呈現狀態、進度、功率、累積用電、費用與工具紀錄。
3. 沒有可行時段或缺少資訊時，清楚說明並要求使用者調整／補充。
4. 原定開始時間錯過後，Agent 可在核准限制內重新規劃，超出限制則等待重新核准。
5. 設備失聯、Broker 重啟及重複命令不造成重複啟動；狀態未知與設備確定故障分開處理。
6. 控制服務重啟後保留任務及核准紀錄，先核對設備現況再恢復；設備確實故障由人工處理。
7. 人工確認中止後，取得設備狀態再記為已中止，不記為完成。
8. Azure 異常時切到 vLLM；兩者都不可用時仍可由表單產生確定性排程，核准後執行。
9. 60 倍展示與真實時間共用同一套排程／行程／能源邏輯，連線及確認逾時使用真實時間。
