# 智慧家庭 Main Agent 首版實作計畫

更新日期：2026-10-17（Asia/Taipei）。

**狀態：首版程式已實作，離線／假模型、真實 Mosquitto 與 Streamlit 驗證已完成；真實 Azure／vLLM 留待使用者設定後另驗。結果與限制見 [MAIN_AGENT_VALIDATION.md](MAIN_AGENT_VALIDATION.md)，啟動流程見 [MAIN_AGENT_GUIDE.md](MAIN_AGENT_GUIDE.md)。**

## 1. 目標、現況與交付範圍

以現有專案為主體，建立能使用工具、觀察執行結果並重新規劃的智慧家庭 Agent。目標是實際應用，不以策略比較、MILP 或節能優越性實驗作為主要交付。

現有基礎已完成冷氣純運算模型、每兩秒 MQTT 遙測、Streamlit 監測、Docker Mosquitto 與 `.env` 載入；先前 22 項測試通過。Azure／vLLM 連線欄位已預留，但尚未實作或測試模型呼叫。

首版交付：

- 保留冷氣監測，新增一台虛擬洗衣機，一次只允許一個未完成的洗衣任務。
- 自然語言需求、Main Agent 多輪 ReAct、工具紀錄、可驗證計畫及使用者核准。
- 到時執行、設備狀態確認、核准限制內改排、人工取消／中止、異常與重啟恢復。
- 真實時間與 60 倍展示模式、模擬時間電價與用電／費用紀錄。
- Azure OpenAI 主用、vLLM 備援；兩者不可用時仍可透過表單與確定性排程工具操作。

最終架構目標是 **Main Agent 協調 Sub Agents**。首版先由單一 Main Agent 使用工具完成全流程；後續增加洗衣、冷氣等 Sub Agents，共用核准、設備狀態與執行服務。

Matter、冷氣自動控制、實際電價及完整帳單計算為後續階段。實際電價需求持續追蹤於 [TARIFF_ROADMAP.md](TARIFF_ROADMAP.md)。訪談決策見 [INTEGRATION_DECISIONS.md](INTEGRATION_DECISIONS.md)。

## 2. 架構與職責

延續 `src/smart_home_energy/`，以職責分組，使用具型別標註的函式與 dataclass。沿用簡單、明確的模組，不引入多套 Web 框架或通用工作流平台。

| 部分 | 職責 |
| --- | --- |
| 模擬模型 | 洗衣階段、進度、功率與用電積分；接受外部提供的經過秒數，不依賴 MQTT、資料庫或畫面 |
| 時間與電價 | 提供一致的邏輯時間、時段費率及分段費用計算 |
| 排程領域邏輯 | 搜尋合法候選時段，驗證期限、安靜時段、完整行程及費用上限 |
| SQLite 儲存 | 任務、計畫版本、核准範圍、命令、設備快照、事件與 Agent 工具紀錄 |
| 虛擬洗衣機程序 | 自主推進行程，處理 MQTT 命令、命令去重及狀態回報；通訊中斷時已開始的行程仍持續模擬 |
| 控制服務 | 常駐背景程序，執行核准計畫、核對設備回饋、產生事件，與模型推論分開運行 |
| Main Agent | 事件驅動的多輪 ReAct，選擇工具、讀取結果、提出／調整計畫及查核執行 |
| Streamlit | 輸入需求、補充條件、核准、取消／中止、查看進度與紀錄；不承擔背景排程生命週期 |

運行邊界：Mosquitto、既有冷氣模擬器、虛擬洗衣機、控制服務與 Streamlit 可分別啟動。關閉瀏覽器不停止核准任務；模型請求不阻塞排程與 MQTT 接收。

例外捕捉集中於設定、模型 API、MQTT 解碼及服務入口。領域函式回傳明確結果或拋出具體錯誤，不使用 `except Exception` 隱藏故障；生命週期使用 `finally` 清理資源。

## 3. 模型、時間與排程規則

### 已確認的預設值

| 項目 | 預設 |
| --- | --- |
| 洗滌 | 30 分鐘、200 W |
| 漂洗 | 15 分鐘、100 W |
| 脫水 | 15 分鐘、400 W |
| 完整行程 | 60 分鐘，標準模型總用電 0.225 kWh |
| 模擬尖峰費率 | 08:00–22:00，NT$6/kWh |
| 模擬離峰費率 | 其餘時段，NT$2.5/kWh |
| 安靜時段 | 預填 23:00–07:00，可修改或取消 |
| 時間模式 | 預設真實時間，展示模式 60 倍 |
| 自動改排費用上限 | 核准時可調，預填該計畫預估費用；儲存完整精度，不以畫面四捨五入值判斷 |

這些是可修改的教學參數，畫面明確標示模擬設備、模擬電價與預估費用。連線及簡單數值設定集中於 `.env`；行程設定載入後以資料物件傳入模型。

### 時間規則

- 排程、洗衣進度與用電／電費積分使用同一份可注入的邏輯時鐘；控制服務與虛擬設備共享持久化的時鐘識別碼、時間基準與倍率。
- 傳輸時間戳、資料新鮮度、Agent／命令逾時使用真實時間；預算與逾時使用單調時鐘，不受加速倍率影響。
- 儲存有時區的時間，統一以 UTC 表示，輸入與畫面採 Asia/Taipei。遙測另帶邏輯時間，不把加速後的時間戳拿來判斷在線狀態。
- 時間模式及倍率在無未完成任務時才可切換；切換後產生新的時鐘識別碼，舊計畫不能直接沿用。

### 排程與費用規則

- 任務指定最早開始、最晚完成、可選的每日禁止運轉區間，以及洗衣行程；支援跨午夜與隔日日期。
- 以一分鐘為候選開始時間解析度，選擇可完成整個行程、且任何階段均不碰到禁止時段的候選；成本相同時選較早開始。
- 費用依每個階段與電價時段的重疊秒數積分；跨階段、費率切換及午夜時要拆分區間。
- 查詢不足時補問；沒有合法候選時提供衝突原因，不默默修改期限、安靜時段或費用上限。
- 核准畫面顯示確切日期、開始／完成時間、行程、限制、模擬費率、預估費用與可自動改排的費用上限。
- 從提案到核准、改排提交及實際啟動前都重新驗證時間與版本，防止推論延遲造成過期計畫被執行。
- 已核准的行程參數與費率版本保存快照；設定檔變更不直接改動現有任務的核准內容。

## 4. 任務、工具與 MQTT 介面

### 任務及核准

最小資料物件包含：`TaskConstraints`、`WashProgram`、`Plan`、`ApprovalEnvelope`、`DeviceState`、`DeviceCommand`、`CommandResult`、`AgentEvent` 及 `AgentRun`。

- 任務包含識別碼、版本、限制、計畫及狀態；核准範圍記錄使用者允許的期限、運轉時段、行程與費用上限。
- 狀態涵蓋補充資料／待核准、已排程、啟動確認中、運轉中、中止確認中、完成、取消、已中止、失敗及狀態未知。
- SQLite 交易保證同時最多一個未完成任務；狀態未知時仍佔用該名額。故障需人工處理並核對設備恢復後，才能開始新任務。
- 使用者在畫面核准，Agent 工具沒有自行核准的能力。任務更新要檢查預期版本，拒絕過期 Agent 工作修改新版本。
- 未開始的任務可在原核准範圍內自動改排，保留新版本與原因；超出範圍則回到待核准。
- 啟動前可取消；運轉中必須人工再次確認後才能中止。收到設備已中止狀態才記為中止，未確認時維持未知／確認中。

### Main Agent 工具

首版工具集：`get_home_state`、`get_device_state`、`get_task_state`、`get_tariff`、`find_schedule`、`validate_plan`、`propose_plan`、`reschedule_task`、`verify_execution`。人工核准及人工強制中止由 UI／控制服務處理，不開放 Agent 代替使用者執行。

- Main Agent 讀取事件及任務上下文，自行選工具、讀取工具結果，再決定下一個動作或完成／補問。
- 工具採明確、可驗證的 JSON 輸入輸出；數學計算與限制檢查交給工具，工具結果再回到 Agent 迴圈，而非一次 LLM 回覆就結束。
- 首版使用通用 JSON 動作協議（工具名稱、參數、簡短決策摘要），在應用層執行白名單工具，不要求 vLLM 已啟用原生自動 tool calling。格式錯誤可在回合限額內修正，不能執行任意函式或 shell。
- Agent 工作契約保留角色、任務上下文、工具集合與結構化結果，之後可增加 Sub Agent 委派工具；首版不建立沒有實際行為的 Sub Agent 空殼。

### MQTT 與相容性

保留既有 `MQTT_TOPIC` 與冷氣遙測格式，避免破壞現有 PoC。新增洗衣控制協議及依設備識別碼管理的狀態；不要讓洗衣機被迫提供室溫欄位，也不要用單一 `run_id`／序號清除不同設備的歷史。

新協議以 `HEMS_MQTT_ROOT` 作為可設定根主題，範本使用 `home/hems`：

| Topic | 用途 | 發送政策 |
| --- | --- | --- |
| `<root>/devices/washer-1/state` | 最新設備快照 | QoS 0、retain |
| `<root>/devices/washer-1/command` | 啟動、停止、查詢及人工故障解除 | QoS 1、不 retain |
| `<root>/devices/washer-1/result` | 命令受理／拒絕結果 | QoS 1、不 retain |

- 新訊息包含協議版本與 `device_id`。狀態包含設備啟動識別碼、序號、真實觀測時間、邏輯時間／時鐘識別碼、任務／行程識別碼、階段、進度、功率、用電與故障資訊。
- 命令包含唯一 `command_id`、任務／計畫版本、動作及真實過期時間；設備拒絕過期、錯誤時鐘或不相容狀態的命令。
- 設備以交易保存命令結果與行程狀態；重複命令回報既有結果，不建立新行程。傳輸成功、命令受理、行程完成是不同狀態。
- 命令確認等待 5 個真實秒，逾時先讀取狀態；不盲目重送啟動，也不把沒有 ACK 當成設備已停止。
- 通訊斷線不使已開始的模擬行程自行中止；真正設備故障則將任務標記失敗，等待人工處理。
- 虛擬設備程序重新啟動且無法證明行程連續執行時，回報需要人工處理的故障，不能臆測離線期間已完成。

## 5. 背景執行、恢復與模型備援

### 本機執行與儲存

- SQLite 保存任務、核准範圍、計畫版本、UI 請求、命令、設備快照、Agent 事件及工具紀錄。使用明確交易、每個執行緒自己的連線與 WAL，不建立額外 ORM 抽象。
- UI 透過帶識別碼的持久化請求提交建立、核准、取消、中止或故障解除；控制服務驗證並處理，避免 Streamlit 重繪重複觸發操作。
- 控制服務每個真實秒檢查排程與回饋；新需求、狀態不符、錯過啟動或設備異常產生持久化事件。
- 相同異常未處理完時合併事件。Agent 推論在獨立工作執行緒處理，與 MQTT callback、排程迴圈隔離。
- 控制服務重啟後恢復待處理請求與事件，先查設備現況，再恢復任務；不直接重送持久化的舊啟動命令。
- 保存行程、命令與狀態的識別碼，用於確認已完成、仍在執行、確定故障或未知；未知狀態不允許建立第二個行程。

### 模型連線

使用官方 OpenAI Python SDK 的 Chat Completions 介面。實作當日重新核對 Azure 與 vLLM 文件，安裝並記錄相容 SDK 版本。

- Azure：由 `AZURE_OPENAI_ENDPOINT` 組成 v1 base URL，`model` 傳入 `AZURE_OPENAI_DEPLOYMENT`，使用 `AZURE_OPENAI_API_KEY`。
- vLLM：`VLLM_BASE_URL` 包含 `/v1`，模型使用 `VLLM_MODEL` 的 served model name；Key 依服務設定填入。
- 真實連線值由使用者自行填入 `.env`；未設定時不阻擋 MQTT 監測與表單排程。
- 不因開啟頁面自動測試付費模型；在明確的新需求／事件啟動 Agent 時才呼叫服務。

執行保護預設已接受：

- 一次 Agent 工作最多 **15 次模型請求**，包含備援嘗試；總時間最多 **120 個真實秒**；單次最多 **20 個真實秒**，且受剩餘總預算限制。
- 停用 SDK 隱含重試，讓請求次數與時間可控。
- Azure 連線失敗、逾時、限流或服務端異常時切至 vLLM；該次工作後續沿用備援，避免每一回合重新等待故障的 Azure。
- 切換保留上下文與已完成的工具結果，不重做有副作用的工具。設定／授權錯誤需明確呈現，不進行無限重試。
- 兩邊都不可用或耗盡工作預算時，留下失敗原因並提供表單排程；本機執行器繼續處理已核准任務。
- 記錄事件、工具呼叫、結果、簡短決策摘要、實際供應者、請求次數與耗時；不保存 API Key 或要求展示模型私有推理全文。

格式參考：[OpenAI Python SDK](https://developers.openai.com/api/reference/python)、[Azure v1 API](https://learn.microsoft.com/en-us/azure/foundry/openai/api-version-lifecycle)、[vLLM OpenAI 相容服務](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/)。

## 6. 實作順序與驗收

每個階段完成相應測試後再往下，避免同時加入模擬、控制及模型變更。

1. **領域模型與時間／電價。** 新增分階段洗衣、邏輯時鐘、費率及候選排程，先用純函式測試跨夜、安靜時段及分段積分。
2. **SQLite 與任務生命週期。** 完成單一任務限制、版本、核准、取消／中止、請求／事件與恢復資料；先驗證沒有模型也能運作。
3. **MQTT 設備與控制服務。** 完成真實 Broker 的啟動、狀態讀回、命令去重、斷線及重啟；保留原冷氣 PoC。
4. **Main Agent。** 建立白名單工具、多輪 ReAct、事件觸發、Azure／vLLM 備援及請求預算。以可重現的假模型回覆測試工具流程，再於使用者設定服務後驗證真實模型。
5. **Streamlit。** 加入自然語言入口、補問、表單降級、計畫核准、進度／功率／費用、人工操作及工具紀錄；UI 重繪不得重複提交請求或建立背景執行器。
6. **整體驗收與文件。** 更新依賴、`.env.example`、PowerShell 啟動／停止流程、來源說明與驗收紀錄。

必要驗收：

- [x] 標準行程為 60 分鐘、0.225 kWh；一次跨多個階段的時間步長仍正確積分。
- [x] 跨電價邊界的費用正確；跨夜及禁止時段不造成違規候選；沒有可行方案時不自行放寬限制。
- [x] Main Agent 實際完成多輪不同工具呼叫，根據工具結果決定下一步；不是一次回覆後由畫面假裝執行。
- [x] 未核准計畫、錯誤設備、過期版本及超出核准範圍的改排不能啟動設備。
- [x] 核准範圍內自動改排成功，超出費用／期限／時段範圍會等待重新確認。
